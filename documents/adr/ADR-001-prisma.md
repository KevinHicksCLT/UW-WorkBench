# ADR-001: Keep Prisma as the ORM (properly configured)

**Status:** Accepted — 2026-07-02
**Charter:** Task 15 (Evaluate Prisma — right tool for the job)

## Context

The charter asked whether Prisma is the correct, most performant tool, citing that it
"feels clunky and is generating unexpected files," and that the incoming team knows
little about databases, so setup must be easy and repeatable.

## Investigation

1. **"Random file creations."** The unexpected files are Prisma's generated client
   (`backend/node_modules/.prisma/client`, regenerated by the `postinstall` hook) and,
   historically, `prisma db push` shadow artifacts. These are **expected tooling
   behavior**, live under `node_modules` (never committed), and disappear as a concern
   once understood. Verdict: *misconfigured expectations, not a wrong tool.*
2. **Performance.** Profiling the slow endpoints (see `documents/refactor-baseline/`)
   shows latency comes from query *patterns* (multiple sequential round-trips to a
   remote Neon instance, double hydration, in-memory joins over large sets) — not from
   Prisma overhead. The same patterns would be slow on any ORM. The closure-table walks
   that genuinely exceed ORM expressiveness already use `$queryRaw` (8 call sites, all
   parameterized) — the correct escape hatch, used sparingly.
3. **Fit with this codebase.** 94 models, all FK columns explicitly indexed, one
   generated type-safe client consumed by 66 backend files. TypeScript-first types are
   the single biggest onboarding aid for a team that "knows little about databases."
4. **Alternatives considered.**
   - **Drizzle** — lighter, closer to SQL; but migrating 94 models + every query in the
     app is weeks of high-risk churn for marginal gains, and its migration story is no
     stronger for this workflow.
   - **Kysely / raw SQL** — maximum control, but removes the type-safe model layer the
     incoming team needs most.
   - **TypeORM/Sequelize** — weaker type safety; no advantage.

## Decision

**Keep Prisma**, and fix the workflow instead of the tool:

- **Version-controlled migrations are now the only way schema changes happen** (charter
  Task 18). The drifted `db push` history was squashed into a single
  `backend/prisma/migrations/0_baseline/` migration on 2026-07-02 (old migrations
  archived in `backend/prisma/_migrations_legacy/`). Every environment marks the
  baseline applied once (`npx prisma migrate resolve --applied 0_baseline`) and then
  uses `prisma migrate dev` (locally) / `prisma migrate deploy` (Vercel build) forever.
- `prisma db push` is **deprecated for this repo** — it drops drifted columns silently
  (documented incident history). Use `npm run db:migrate -w cascade-backend`.
- One-command local setup: `npm run db:setup -w cascade-backend`
  (generate → migrate deploy → seed).
- `schema.prisma` and `documents/value-streams/Master Documentation/erd_v5.mmd` stay in
  lockstep (enforced by the `db-data-model` skill; verified in this refactor — in sync).

## Consequences

- New environments (Neon branches) forked from an existing branch inherit the schema
  and the `_prisma_migrations` ledger — `migrate deploy` is a no-op until a new
  migration lands. Fresh empty databases build fully from `0_baseline`.
- `develop` and `production` Neon branches have **no `_prisma_migrations` table yet**;
  before the first deploy of this branch's pipeline, run the baseline-resolve step
  (documented in `documents/refactor/CUTOVER.md`).
