How a proposed change (retire, consolidate, replace…) is assessed against the live operating-model graph before it is applied — the deterministic walk, the two AI enrichment passes, and the frontend gate that holds the pending action until the user confirms from the report.

1Overview & design principles

The change impact assessment is a pre-decision gate. Every Workspace lens (Products, Value streams, Roles, Applications) routes its destructive or restructuring actions through one mechanism: the action is captured as a pending callback, an impact report is computed against the live graph, and the callback only executes when the user confirms from that report.

Principle 1 — derived on read, never persisted. A report is computed from the closures and junctions at request time. Nothing is written, nothing is cached (routes/impact/index.ts deliberately applies no cacheResponses). A report must reflect the graph at the moment the user is about to decide.
Principle 2 — the graph walk is ground truth; AI is enrichment. The deterministic report from /impact/assess stands alone. The AI summary and deep-dive add narration and derived consequences, are badged as such, and on any failure or timeout silently return nothing — they can never block or fail the assessment.
Principle 3 — every domain always answers. Six knock-on domains (product, technology, data, operational, compliance, testing) are always rendered. An empty domain card reads as “checked — no impact found”, never “not checked”.
Principle 4 — no per-row fan-out. Walkers batch-load junctions with single { in: ids } queries, resolve ancestry once through the shared resolvers, and aggregate in memory. Itemized output is capped at 10 lines per rule; the remainder collapses to one aggregate line.

3End-to-end sequence

Timing model. The deterministic report typically lands in one round-trip of batched queries. The panel keeps the scanner visible while s.loading || ai.loading — the report view appears only when the deep-dive resolves (or fails to empty). The summary strip renders whenever it arrives; it never gates anything. The scanner’s six “locking” steps are a fixed 2.3 s cadence over a single-shot call — presentation, not real per-system progress.

4API contracts

POST /impact/assess

Pure read carried as POST (subjects hold id arrays). Auth: JWT via requireAuth; tenant resolved by activeCompany(req) — cross-tenant ids simply fail the walker’s companyId filter and 404.

// Request body (zod, assess.ts)
{
  changeType: 'RETIRE'|'DROP'|'DEPRECATE'|'REPLACE'|'MERGE'|'CONSOLIDATE'|'MOVE'|'ADOPT'|'HOLD',
  label?: string,                       // ≤300, overrides subject display name
  subject:                              // discriminated union on `kind`
    | { kind:'process-nodes', nodeIds: string[] }          // 1..200
    | { kind:'role', roleId: string, taskIds?: string[] }  // taskIds ≤500 narrows to step scope
    | { kind:'application', applicationIds?: string[],     // ≤50 estate apps
        rationalizationAppIds?: string[] }                 // ≤50 board apps
    | { kind:'product-element', lobId: string, component: string,
        elementName?: string, componentNodeIds?: string[] } // ≤100
}

// Response 200: ImpactReport
{
  subject: { kind, id, name, context },
  changeType, changeClass: 'destructive'|'restructure'|'adopt',
  summary: { breaking, high, medium, low, total },
  impacts: Impact[],        // sorted domain → severity → entityName
  score?: DecisionScore,    // product-element only
  goal?:  GoalProgress      // product-element only
}
// Impact line
{ severity, domain, category, entityType, entityId|null, entityName, description, count? }

// 400 invalid body · 404 no company / subject not found · 500 via central error handler

POST /impact/summary

// Request: digest of an already-computed report (client-built, re-validated)
{ subject:{kind,name,context?}, changeType,
  summary:{breaking,high,medium,low}, impacts: ≤40 × {severity, domain?, category, entityName, description} }
// Response — ALWAYS 200 unless body invalid:
{ summary: string | null }   // null on: no ANTHROPIC_API_KEY, 4s timeout, any AI error

Model IMPACT_AI_MODEL (default claude-haiku-4-5-20251001), max_tokens 220, maxRetries 0 (a retry cannot finish inside the budget), Promise.race against a 4 000 ms unref’d timer.

POST /impact/analyze

// Request
{ changeType, subject: <same subjectSchema as /assess>, subjectName,
  subjectContext?, reportLines: ≤60 × {domain, severity, entityName, description} }
// Response — ALWAYS 200 unless body invalid / no company:
{ impacts: Impact[] }   // [] on: no key, 60s timeout, bad AI shape
// Derived lines: entityType 'DerivedImpact', entityId null,
// category mapped from domain: product→products, technology→applications,
// data→applications, operational→tasks, compliance→compliance, testing→testing

Model IMPACT_ANALYZE_MODEL (default claude-sonnet-5), max_tokens 4000, maxRetries 1, 60 000 ms race. Output is a forced tool call (tool_choice: {type:'tool', name:'report_impacts'}) so the response arrives as parsed JSON — a long generation can never truncate into an unparseable string. unwrapImpacts() then normalizes wrapper variance (bare array, double-wrapped object, stringified payload — up to 4 unwrap steps) before zod validation.

Assembly helpers

6The four graph walkers

All walkers share the same shape: verify tenant → expand scope → batch-load every junction the scope touches in one Promise.all → apply the rule table → grade → cap → build. The recurring analytical move is the sole-vs-co distinction: an entity that exists only inside the change scope grades BREAKING (nothing left after a destructive change); one that also exists outside grades softer (workload shifts, doesn’t vanish).

7Product extras: decision score & goal progress

Only product reports carry score and goal. Both are deterministic — no AI involvement.

GoalProgress reuses the products-board pipeline (loadSpine → scopeLobs (latest generation per product, no filters) → buildHeatmap with persisted decisions) to state “LOB is X% normalized — N of M decisions made”. Wrapped in try/catch returning undefined: the strip is enrichment and never fails the assessment.

Grounding chain: the AI never queries the database freely. /analyze builds a compact context pack server-side (capped lists, sliced descriptions), concatenates it with the deterministic report lines, and the system prompt binds claims to those two sources. Derived lines are tagged entityType:'DerivedImpact' and wear the same category vocabulary as graph lines so the cards read as one report; the frontend additionally badges them via the aiGenerated flag on merge.

9Frontend: gate & panel

Gate mechanics (useImpactGate.ts)

  • run(request, proceed, onCancel?) stores proceed in a ref and POSTs /impact/assess with invalidate:'none' — the assessment is a pure read and must not wipe the warm GET cache.
  • seqRef increments on every run/cancel/confirm; a stale assess response comparing unequal is dropped — a cancelled panel can never be resurrected by a late response.
  • confirm(chosen?) sets busy, awaits proceed(chosen); success closes the panel, a throw surfaces as an inline error with the panel still open.

Panel rules (ImpactPanel.tsx)

  • Portal on document.body, zIndex 70 — stacks above ReviewModal (60), which stays open underneath.
  • scanning = s.loading || ai.loading — one scan phase covers graph walk and deep-dive; the six-card report appears only when the full analysis is in.
  • Merged lines = graph impacts (already sorted) followed by AI impacts sorted by severity; cards filter merged lines by domain; severity totals count the merged set.
  • Product subjects: footer is the decision — Retain / Standardize / Retire map to HELD / APPROVED / RETIRED; buttons lock until scanning completes; the score’s recommendation earns a ★ (STANDARDIZE→APPROVED, RETAIN→HELD, RETIRE→RETIRED).
  • Other subjects: single Proceed button, red when the verb is destructive.
  • Assess failure: warning renders, Proceed stays available — “consequences have not been reviewed” is stated, not enforced.

Invariants (hold these when extending)

  • The assessment path performs zero writes — any mutation belongs in the caller’s proceed().
  • Every impact line belongs to exactly one of the six domains; the panel renders all six unconditionally.
  • Every base severity passes through grade() — never hardcode a graded severity (the two deliberate exceptions are LOW scope lines and the product in-force BREAKING line, which is destructive-only by condition).
  • New itemizable rules go through pushCapped; aggregates must carry count.
  • AI responses are validated (zod) and normalized (unwrapImpacts) before use; a bad shape degrades to empty, never to a 500.
  • Frontend types in impact/types.ts mirror backend routes/impact/types.ts — change them together.
